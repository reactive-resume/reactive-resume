Reactive Resume uses one Vercel project: static web assets on the CDN and the shared Hono server in a Node.js 24 Function. Docker remains supported with the same API, authentication, templates, and application data format.

## Requirements

- A Vercel account and Git provider account.
- Neon PostgreSQL, Upstash Redis, and a **private** Vercel Blob store, connected through Vercel Marketplace.
- Three independent random secrets: `AUTH_SECRET`, `ENCRYPTION_SECRET`, and `CRON_SECRET`. Generate each with `openssl rand -hex 32`, and save them in your password manager. Keep their values across redeployments.

Vercel Hobby supports the configured 300-second Function budget. On both Docker and Vercel, each agent run stops active work after four minutes, leaving time to save and clean up. This is a limit per question/run, not per conversation. Follow-up questions start a fresh timer. Typical shorter answers return immediately. Completed edits and history remain saved after a timeout.

Service quotas and permitted use depend on your Vercel and database/storage plans. Check [Vercel limits](https://vercel.com/docs/functions/limitations), [Neon](https://vercel.com/marketplace/neon), and [Upstash](https://vercel.com/marketplace/upstash/upstash-kv) before choosing a plan. Disable automatic paid upgrades if you want a fixed free allowance.

On Hobby, select your **personal GitHub account** as the Git scope. Private repositories owned by a GitHub organization require Vercel Pro.

The deployment wizard clones the repository, requests the three services, and asks for the three secrets. Select compatible nearby regions, preferably `iad1` for the default Function region. Review provider terms and pricing in the wizard. Blob access must be **private**.

Leave the project root at the repository root. Use the committed `vercel.json`; do not select the web app subdirectory or override it with an SPA fallback. The build generates both applications, then applies database migrations before publishing. No separate migration command is needed.

After deployment:

1. Open the production domain and create an account.
2. Check `/api/health`; database, Blob, and configured Redis should be healthy. A cold database may need a second check.
3. Add an AI provider and its API key in application settings if you want AI features.
4. Configure SMTP for verification/recovery emails. Without SMTP, messages appear in server logs.
5. Add optional OAuth credentials using the callback URLs shown in the [SSO guide](/self-hosting/sso).

Do not paste Docker's entire `.env.example` into Vercel: its local URLs and S3 defaults select the wrong services.

## Configuration

| Variable | Behavior |
| --- | --- |
| `APP_URL` | Optional on Vercel. Defaults to the stable production domain, or the current deployment domain in preview. Set explicitly for a custom domain. |
| `DATABASE_URL` | Pooled Neon runtime connection. `POSTGRES_URL` is accepted as a fallback. |
| `DATABASE_MIGRATION_URL` | Direct migration connection. Defaults to `DATABASE_URL_UNPOOLED`, then `POSTGRES_URL_NON_POOLING`, then runtime URL. |
| `DATABASE_POOL_MAX` | Maximum connections per Function instance; defaults to 10. |
| `REDIS_URL` | Redis TCP/TLS URL. Upstash's `KV_URL` is accepted as a fallback. REST API credentials alone are insufficient. |
| `STORAGE_BACKEND` | Vercel requires `blob`; Docker defaults to S3 when configured, otherwise local disk. |
| `BLOB_READ_WRITE_TOKEN` | Injected by the connected private Blob store. The SDK also supports `BLOB_STORE_ID` with Vercel OIDC. |
| `AUTH_SECRET` | Persistent authentication secret. |
| `ENCRYPTION_SECRET` | Persistent encryption key for saved AI-provider credentials; at least 32 characters. Losing it makes those credentials unreadable. |
| `CRON_SECRET` | At least 32 characters. Vercel sends it to the authenticated daily staging-cleanup job. |
| `DEPLOYMENT_NAMESPACE` | Defaults to `production` on Vercel, a branch/deployment namespace in preview, and `default` on Docker. Keep stable after storing files. Use different explicit namespaces if multiple projects share Blob or Redis. |
| `ALLOW_PREVIEW_MIGRATIONS` | Preview builds fail unless set to `true`, after connecting an isolated preview database. |

Explicit connection variables take precedence over Marketplace aliases. Use separate resources for separate application installations. Adding a custom domain does not change the storage namespace. Update `APP_URL`, OAuth callback URLs, and redeploy when changing the public origin.

## Uploads and private files

Vercel's ingress limit is smaller than the application's supported file sizes. The web app sends large serialized RPC bodies directly to a private staging object, then submits an authenticated one-use reference. The server restores the original request and applies the existing authorization, limits, image resizing, import parsing, and attachment quotas.

General uploads retain their 10 MB limit; agent attachments retain their 25 MiB per-file and 100 MiB per-thread limits. The staging transport accepts up to 160 MiB of serialized RPC data, including base64/framing overhead. Split larger batches. Ordinary Docker requests keep their original transport.

Public pictures are served through application upload routes; Blob objects themselves remain private. Agent attachment authorization is unchanged. Successful and failed finalizations clean up staging objects immediately. Abandoned objects become eligible after ten minutes; later uploads and a daily authenticated job remove expired objects in bounded batches.

External RPC clients sending large requests can use the same protocol:

1. `GET /api/storage/stage` returns `{ enabled: true }` on Vercel.
2. Serialize the original `POST /api/rpc/...` request. With the same session, API key, or bearer token, `POST /api/storage/stage` with JSON `{ path, contentType, size }`. `path` includes the original query string. A browser must send the configured application origin.
3. `PUT` those exact bytes to the returned `url`, using `Content-Type: application/octet-stream` and no application credentials.
4. Send the original RPC URL and authentication headers, with an empty body and `x-resume-staged-body: <id>`.

References are bound to the authenticated user and exact RPC path, expire after ten minutes, and may only be consumed once. A failed finalization needs a new upload; do not blindly retry a mutation whose response was lost. Direct OpenAPI/MCP bodies remain subject to Vercel's ingress limit; large imports should use the RPC staging protocol.

## Updates, previews, and recovery

Redeploy the same project and retain its connected resources and secrets. Migrations run outside the build cache and use an advisory lock to serialize concurrent deployments. Runtime Functions never run migrations. Docker still runs them at startup.

Preview deployments must use their own database and separate credentials. Connect isolated preview services before setting `ALLOW_PREVIEW_MIGRATIONS=true`; a namespace alone cannot isolate SQL rows. Never connect production databases to untrusted preview code.

Back up PostgreSQL and Blob, and preserve the secrets separately. Reverting a code deployment does not undo database migrations; use backward-compatible migrations or restore an appropriate database backup. Moving between Docker and Vercel does not automatically copy databases or storage objects.

For a local Vercel artifact build, run `vercel pull --environment production`, supply local-only replacements for sensitive placeholders, then run `APP_URL=https://your-project.vercel.app vercel build --prod`. The local CLI has no deployment hostname before publishing. Use an isolated database because this command applies migrations. Cloud builds receive the hostname automatically.

## Troubleshooting

- **First build fails on configuration:** verify all three stores are connected to Production and all three secrets are present. Remove accidental S3 variables.
- **Preview refuses migrations:** connect an isolated database, then explicitly enable preview migrations.
- **Large upload returns 413:** use the web app or RPC staging protocol. Pro does not remove the ingress limit.
- **Agent reconnect/stop fails:** verify Upstash's Redis TLS URL, available quota, and matching namespaces across instances.
- **Sign-in redirects to another hostname:** set `APP_URL` to the domain you use and redeploy; do not use wildcard trusted origins.
- **Files disappear after changing configuration:** restore the original `DEPLOYMENT_NAMESPACE` and Blob connection. Do not generate a new namespace per production deployment.

## Deployment checks

Pull requests build a complete Vercel artifact using isolated PostgreSQL and dummy cloud credentials. This checks migration preparation, Node.js 24 module loading, and the 300-second Function configuration without exposing deployment credentials to forks.

The manual **Vercel compatibility** workflow runs authenticated smoke checks against `VERCEL_SMOKE_URL` in the `vercel-smoke` GitHub environment. Use a dedicated test installation: the check creates and deletes its own account, renders a public PDF, and transfers a 10 MiB file. For 25 MiB agent attachment checks, configure `VERCEL_SMOKE_AI_BASE_URL` and the `VERCEL_SMOKE_AI_API_KEY` secret for a deterministic OpenAI-compatible test provider with model `smoke-model`. These checks never need a paid AI model.

Run the same core checks against Docker with `SMOKE_URL=http://localhost:3000 node tooling/deployment/smoke.mjs`.
