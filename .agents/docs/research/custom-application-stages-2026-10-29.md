# Custom application stages: feasibility and migration

Research date: 2026-10-29. Request: [#3518](https://github.com/reactive-resume/reactive-resume/issues/3518), including linked [#3234](https://github.com/reactive-resume/reactive-resume/issues/3234). Source baseline: `aeb82c68b6840ef1e6c45e99de40bd960c4f8fb9`, matching remote `main` when checked. This is a feasibility assessment, not an implementation or migration rehearsal.

**Verdict:** feasible, with an additive migration and preserved behavior, provided custom lanes have stable identities and explicit workflow categories. Existing components will not support arbitrary new status strings unchanged. This is a coordinated schema/API/web/mobile feature, not a board-only setting.

## What already exists

The issue describes the older Saved / Applied / Screening / Interview / Offer / Rejected pipeline. Current code has Saved / Applied / Screening / Interview / Offer / Closed. Closed has reasons including `no-response`, so the underlying outcome requested as “Ghosted” already exists as **Closed → No response**. A distinct, reorderable Ghosted lane and a warning about applying to that company again do not follow from that existing outcome. The schema explicitly anticipates promoting stages to a table if per-user stages become necessary. [S1]

The database stores status as text, with a TypeScript type, rather than a PostgreSQL enum. This simplifies an additive migration, but application DTOs, timeline schemas and both clients still assume the six fixed values. The existing v6 migration already translates older `rejected` / `archived` records and timeline entries; a new migration should build on that normalized state rather than invent another interpretation. [S2] [S3] [S4]

## Recommended model

Keep two concepts:

- **Lane:** user-owned identity, label, color, display order and retirement state. Add a persisted lane reference to each application.
- **Workflow category:** the existing `saved | applied | screening | interview | offer | closed` meaning. Each lane maps to exactly one category. Retain `application.status` as the compatibility field, maintained by the server from the selected lane.

Examples:

| Lane                 | Workflow category                     | Effect                                                                |
| -------------------- | ------------------------------------- | --------------------------------------------------------------------- |
| Wishlist             | `saved`                               | Still a draft; no sent-document snapshot                              |
| Take-home assignment | `interview`                           | Sent application; contributes to interview-stage metrics              |
| Negotiation          | `offer`                               | Offer-stage application                                               |
| Ghosted              | `closed`, preset reason `no-response` | Closed visibility and reminder behavior; no fabricated employer reply |

These are proposed classifications, not classifications the server can reliably infer from arbitrary labels. A take-home that happens earlier could instead belong to screening. The UI should ask which category a new lane belongs to using plain product language.

The server must validate lane ownership and synchronize category, closure reason and timeline in one transaction. A request containing a lane and contradictory category or outcome should be rejected. Keep an active default lane for every canonical category so legacy writers always have a deterministic destination, independent of display order. Never use a user-editable label as a key or infer business behavior from its spelling.

Keep category assignment stable after a lane has been used, or make reclassification a separate explicit operation with historical semantics preserved. Renaming or reordering a lane must not change whether an application was sent, received a reply, reached an offer, or closed. No configurable automation engine is needed for this request.

Own lane resolution and the category/lane/timeline transition invariant in the application service, callable within existing transactions. Reuse that operation from CRUD, bulk/import and Career writers instead of maintaining parallel rules. Career-specific submission snapshots and retry checks should remain with their current workflow owner.

### Two easy-to-miss invariants

**Same-category moves:** the current SQL appends a stage event only when `application.status` changes. Interview → Take-home, both classified as Interview, would otherwise produce no event. Both boards also track pending moves by status, and detail hydration only checks status/reason. A lane table alone would leave history, duration and optimistic rendering incorrect. Extend existing `type: "stage"` events additively with lane identity and immutable canonical context; do not replace their canonical stage or require old consumers to understand a new event type. The summary DTO and SQL projection both need the new lane field. [S46] [S47] [S7] [S17] [S18] [S38] [S41]

Timeline date edits/deletions need special attention: `appliedAtFromTimeline` currently selects the latest Applied event. Logging an Applied → Applied-category lane move without adapting that helper could later change `appliedAt` merely by editing a timeline date. Distinguish lane-visit anchors from actual canonical transitions/submission anchors. [S39] [S40]

**Display order is not historical progression:** Insights currently uses a fixed semantic pipeline and assumes later categories imply earlier progress. Using a user's arbitrary column order in that calculation could make reordering columns change response rates, sent dates or offers without any application action. Retain canonical milestone calculations; if exact custom-stage conversion is later required, derive it from recorded visits rather than column positions. The existing inferred milestone metrics should not be represented as proof that every intermediate stage was actually visited. [S15] [S16]

## Integration review

- **Public contracts are shared, but not automatic end to end.** REST application routes bind the same DTOs and service as RPC; OpenAPI spreads that router. The summary DTO uses an explicit field pick and its service uses an explicit SQL projection, so adding a database column alone will not return it everywhere. MCP create/update/import/bulk tools derive much of their input/output from DTOs, but List Applications declares its filter fields separately. Expose new lane tools intentionally through direct metadata/handlers or the parity allowlist, with behavior annotations; adding API procedures does not grant MCP access automatically. Keep existing canonical status filters, `byStage` output and create's string ID response; add separate lane filters/counts when needed. Regenerate OpenAPI and verify live tools, static discovery, and actual calls agree. [S3] [S22] [S23] [S24] [S25] [S41] [S48]
- **Three Career writers bypass application CRUD.** `applyReply` directly changes status and appends events; `submitApplication` directly changes Saved → Applied with sent-document/answer snapshots and strict retry checks; `trackOpportunity` directly inserts a Saved application. All need the same transaction-aware lane resolution as standard create/import/update/bulk paths. A nullable lane field plus read fallback can hide missing writes but cannot maintain canonical/lane consistency. Preserve opportunity deduplication and submission idempotency. Employer-message proposals currently allow only Screening / Interview / Offer / Closed, cannot select a custom lane, and may close without supplying a reason. Preserve legacy behavior; new explicit lane proposals must validate ownership, category, outcome and metadata revision. [S26] [S27] [S28] [S29]
- **AI must see labels deliberately.** Structured Career generation sends `stage: application.status`; the cross-application coaching tool selects canonical status without lane metadata. Add lane identity/label alongside category if the coach should distinguish Interview from Take-home; treat custom labels as user data under existing sharing consent. Career proposal staleness currently includes application `updatedAt`, not a separate lane-definition revision. If lane metadata enters a prompt or proposal, validate its revision too; rename/retirement must not leave a stale proposal selecting a now-invalid lane. Background discovery stores opportunities; tracking them creates applications only through the explicit tracking action above. No separate autonomous application-status writer was found in the reviewed job/tool paths. [S36] [S37] [S42] [S28] [S30]
- **Closed does not currently stop every schedule.** `requireCareerApplication` checks ownership/interview existence, not status. Career job execution validates schedule/lease/ownership, then can generate a briefing or create a follow-up notice; the email path checks enabled schedules without checking application category. Therefore Ghosted → Closed preserves current native reminder behavior but does not prove scheduled Career coaching/email will stop. If closure should suppress those jobs, add category guards at execution, result publication and email delivery, with concurrent close/reopen tests. This is a product decision and implementation requirement, not existing behavior. [S30] [S43]
- **Exports need lane definitions, not dangling IDs.** Account export queries application rows and validates them through the application DTO, but a new lane table will not be exported automatically. Add owner-scoped definitions, including retired lanes needed by history, to the service and output schema. Web ZIP packaging explicitly chooses files and must include that metadata; native exports the whole account response as JSON. Existing ZIPs are records plus individually importable documents, not a whole-account restore protocol. Do not promise lossless application/lane/history restoration through CSV or document import. Full database backups must include the new table and constraints; restore/rollback remains a separate untested gate. [S31] [S32] [S33] [S34] [S44]
- **Ownership transfer is a migration path too.** Guest-to-account linking updates application `userId` in a transaction, then the guest is removed. A same-owner `(laneId, userId)` constraint requires coordinated transfer/remapping of lane definitions, application references and historical lane IDs; default system keys may already exist in the destination account. Without it, linking could fail its constraint or guest cleanup could remove referenced metadata. Keep account deletion cascading to owned lanes; lane retirement must never cascade to applications. [S35] [S45] [S2]

## Clean migration and mixed-version rollout

1. **Expand schema and read behavior.** Add user-owned lane definitions and a nullable application lane reference. Seed the six existing lanes for existing owners and new accounts. Use unique system keys per owner so seeding is repeatable. Default label keys retain localization; custom labels remain user content. Index ownership and lane lookups; enforce same-owner relationships in both database design and service validation.
2. **Preserve existing rows.** Backfill each application to the lane matching its canonical status. Preserve all row IDs, dates, closure reasons, documents and timeline event IDs. Historical events can display a canonical/default label when lane identity is absent, without claiming that a user visited a later-created lane. Do not manufacture events or sent snapshots. Consider a separate Ghosted lane only for records with `closedReason = no-response`; other closed applications do not establish ghosting. Preserve null outcomes, which existing APIs allow.
3. **Support concurrent old writes.** Until backfill and rollout complete, absent lane references resolve to the appropriate default. Legacy creates/status transitions must maintain the lane mapping too, so concurrent writes cannot leave drift. The backfill must be repeatable and must not overwrite a custom lane already chosen by a newer client.
4. **Add compatible APIs.** Keep existing status fields and endpoint behavior. New clients send lane ID; the server resolves its category. Legacy clients see the canonical stage, so Take-home appears as Interview. A legacy metadata edit or unchanged-status echo must preserve the current custom lane. A deliberate legacy change to another category chooses that category's default lane. An explicit legacy outcome change conflicting with a Ghosted preset should choose the neutral Closed default, rather than leave the label and outcome contradictory. Existing clients cannot express a choice among multiple lanes in the same category.
5. **Ship web and mobile together at feature level.** Load metadata alongside applications; fall back safely while metadata is loading or unavailable. Key native metadata caches by account/server. New clients must detect lane support on an older self-hosted backend and fall back to fixed stages before writing; do not assume an old endpoint will reject an unknown lane-only payload. Keep new response fields optional/defaulted where older servers omit them. Deploy backend compatibility before the mobile update. The proposed feature can plausibly use existing JavaScript/UI dependencies; native fingerprint/build requirements remain to be verified against the actual implementation. [S21] [S3]
6. **Retire lanes safely.** Prefer retirement over hard deletion. Require a replacement for applications currently using a retired lane, with an explicit rule for any category/outcome changes. Keep historical lane identity and display context. Serialize moves against retire/reorder operations and use an expected revision for concurrent settings edits. Do not cascade-delete applications or rewrite their history.
7. **Keep rollback additive.** Roll back application code while leaving new columns/table intact. Old code can operate on canonical statuses, but it will not maintain lane metadata; re-enable compatible writes and reconcile lane/category drift before restoring the feature. Dropping custom metadata after users start using it would lose information, even if canonical statuses survive.

This model permits a data-preserving migration. Execution characteristics and mixed-version correctness need explicit tests; neither is guaranteed merely because the database migration only adds fields. Rollback reconciliation must inspect all write paths above, not just rerun a null-only backfill: old code can change canonical status while leaving a non-null lane pointing to the previous category.

## Ghosted company warning

Treat the optional warning as a separate, user-scoped lookup against `no-response` outcomes, not a match on the lane label. **Current data only reliably identifies applications still marked Closed → No response:** reopening clears `closedReason`, and stage events do not store it. A durable “previously ghosted” warning therefore needs outcome history going forward, including explicit reason changes within Closed; past cleared outcomes cannot be reconstructed reliably. Preserve canonical category and outcome on historical events instead of resolving historical meaning through mutable lane settings. [S38] [S10]

A renamed lane must not erase the warning, and a lane named “Ghosted” with a different category must not create false history. Normalize company spelling conservatively and show matching prior applications; avoid claiming differently named subsidiaries or similarly named employers are definitely the same company. Trigger an advisory warning when saving/submitting another application, not an automatic block or an automatic transition of old applications. No new company-identity service is necessary for a first version. These are design recommendations; the issue does not specify normalization, warning timing, or whether reopened applications should continue to warn.

## Required implementation proof

- Migration fixtures: all six statuses; all closure reasons and null reason; normalized legacy rejected/archived data; empty accounts; repeated/concurrent seeding and backfill; preserved IDs, dates, events and sent versions.
- Service paths: create, direct creation at a later stage, update, bulk update, CSV import, Career apply-reply/submit/track and MCP calls; same-category lane moves log once; repeated no-op moves log nothing; foreign-owner and retired lane IDs are rejected; guest linking handles existing destination defaults.
- Side effects: no duplicate sent versions; submitted-document protections and submit retries survive; Ghosted closes and native reminder cancellation works; agreed scheduled coaching/email behavior holds during concurrent closure; reopen clears current outcome while preserving any recorded historical outcome; same-category Applied events and timeline edits do not falsify sent dates or semantic analytics.
- Compatibility: old client/new server, new client/old self-hosted server, optional new output fields, unchanged-status legacy echoes, null closure reasons, contradictory lane/category/outcome, stale metadata, rename/retirement during drag, concurrent note plus lane move, lost response and optimistic rollback, summary/detail hydration, rollback writes leaving non-null mismatched lanes.
- Contracts and portability: REST/OpenAPI input/output, MCP List/Create/Update/Import/Bulk and lane-tool discovery/annotations, AI context and stale proposals, account JSON and web ZIP lane metadata, account deletion; cross-account import explicitly remaps foreign IDs and does not claim to restore unavailable history.
- UI: web and native board/list/detail/calendar/Insights, bulk actions, accessible lane management/reordering, many columns, long and international names, default label translations and CSV mapping.
