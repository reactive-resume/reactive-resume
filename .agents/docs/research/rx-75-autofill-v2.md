## Source ownership and trust boundaries

Existing private application profile, reviewed-answer/evidence, selected application documents, PDF export and document-history services remain authoritative. Their read helpers now accept the existing transaction connection. Packet review and approval use the existing owner mutex; they do not add autosave, undo, auth or submission owners. Selected documents must be owned, active and available; a linked letter's sender/design source must also be available. Letter wording follows the selected document's language.

Review projects only opted-in profile name/email/phone, visible selected-resume work history including roles, letter text and explicitly selected reusable answers. Sensitive profile fields, hidden work history and editor notes are excluded from projected form fields. Full approved PDFs contain the selected documents' printable content. Answer scope/evidence eligibility is rechecked, not inferred from the client's list. Keyed fingerprints bind source state and selection without exposing guessable hashes of unselected private values.

Approval revalidates before rendering and again after rendering. Rendering uses the current export owner outside the database transaction. Revalidation failure writes no packet versions. Success writes existing named resume/letter versions and returns their exact rendered PDF bytes, SHA-256 hashes and version IDs. No application stage, sent-document reference or submitted-answer snapshot is changed. The combined PDF limit is 2 MiB with a visible manual-download error. Packet copies remain private files under the user's control; they cannot be revoked or silently refreshed.

New authenticated POST routes are `/api/openapi/applications/{applicationId}/packet-review` and `/api/openapi/applications/packets`. Both require read and write permissions, return private/no-store responses and are absent from the MCP allowlist. There is no server fetch of the destination. Account export adds optional `documentVersions`; web ZIP includes `document-versions.json`, native already serializes the complete response. Historical JSON is preserved without current-schema normalization. Existing account/document cascades own deletion. No migration is introduced.

Desktop extends the existing posting-capture helper's `activeTab`/`scripting` surface; capture stays isolated and permissions are unchanged. Imported packets remain in popup memory, never extension storage. Native uses Expo-compatible `react-native-webview` 14.0.1, incognito/no shared cookies, restricted navigation, disabled local-file/universal access and per-page approval. External browser sessions remain separate. Packet JSON and approved PDFs reuse the workspace share/cache owner. That owner now checks account scope before and after asynchronous availability/file writes, removing late files rather than sharing data after an account switch; session cleanup already owns its prefix. The exact shared string script avoids Hermes function-source assumptions. Navigation/load invalidates approval; mismatched destinations fail before writes and after asynchronous file hashing. Reports are untrusted, bounded and request-correlated. Android's message callback reports an origin; iOS reports the frame URL. Reports never authorize a stage change or submission.

The fill engine refuses transparent-ancestor/zero-size controls and emits no input/change/click/submit events, preserves existing values, hashes approved file bytes before assignment and makes no page-navigation or submission call. A filled report means DOM presence only. A site may ignore DOM-only writes or implement its own behavior; employer upload acceptance is unverified. Framework detection is conservative and depends on properties visible in the executing JavaScript realm; isolated extension code cannot establish every framework's state. Unsupported/framework controls require manual verification. This is deliberately not a universal ATS automation claim.
